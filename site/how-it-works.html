How it works

Python robot definition, auto-generated Metal kernel, PPO in MLX with unified memory, then viewer and export.

1. A robot is Python

A Robot is a list of capsules (two endpoints and a radius) and hinge joints (a pivot, limits, a motor gear). There is no file format to learn. Task holds lambdas over a batched State, so rewards are ordinary array math.

2. One Metal kernel per body plan

mg.make reads the body plan and generates a Metal kernel specialized to it: fixed body count, fixed joint list, constants folded in. The kernel runs one GPU thread per robot, so 4,096 robots means 4,096 threads integrating their own planar dynamics, contacts and joint limits in parallel. No Python loop touches individual environments.

The dynamics are deliberately simple: planar (2D), maximal coordinates (every body keeps its own position and angle, joints are constraints between them), a sequential-impulse solver with Coulomb friction against a flat ground, and a few substeps per control step. That is what makes thousands of copies cheap. MuJoCo's HalfCheetah is planar too, so the difference from MuJoCo is not 2D vs 3D: MuJoCo integrates generalized coordinates with a convex, constraint-based contact solver. That is why the benchmarks are not a like-for-like physics comparison.

Contact is tuned so gaits don't skate: we measure stance-foot slip (how far a planted foot slides) and set ground friction so policies have to actually step instead of sliding along the floor.

At small batch sizes the speed is set by fixed per-step overhead (Python and MLX dispatch), not by the kernel, which is why a light robot and a heavy one can run at about the same rate with 1,024 copies. At 16,384 copies the GPU saturates and the physics cost shows up.

3. PPO in MLX

Training is PPO written in MLX: rollouts, advantage estimation, observation normalization and minibatch updates all run on the GPU. On Apple Silicon the CPU and GPU share one pool of memory, so simulator state, observations and network weights never get copied between devices. The sim writes observations, the policy reads them in place.

4. Watch it, ship it

macgym view streams a sample of robots to a browser viewer over a WebSocket. Every robot is drawn on one shared runway with the best highlighted, and the viewer replays earlier generations so you can see the gait improve without reading a number.

When you are happy, policy.export() writes CoreML (for a native app on the Neural Engine) or ONNX (for everything else). mg.to_gymnasium exposes the same env to existing RL libraries.
